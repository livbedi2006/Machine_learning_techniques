## 1. What Does "Framing a Problem" Mean?

Before writing a single line of ML code, the most important (and most skipped) step is converting a **business/real-world problem** into a **well-defined Machine Learning problem**.

> **Definition:** Problem framing is the process of translating a vague business goal (e.g., "reduce customer churn") into a precise, solvable ML task — deciding *what* to predict, *what data* is needed, *what type* of ML problem it is, and *how success will be measured*.

If this step is done incorrectly, no amount of good modeling later can fix it — you'd simply be solving the **wrong problem** very accurately.

---

## 2. Steps to Frame a Machine Learning Problem

### Step 1: Understand the Business Objective
Ask: *What is the actual goal the business/organization wants to achieve?*
- Not an ML term yet — just plain business language.
- Example: "We want to reduce the number of customers who cancel their subscription."

### Step 2: Convert the Business Problem into an ML Problem
Translate the business goal into something an algorithm can learn.
- Example: "Predict, for each customer, the probability that they will cancel their subscription in the next 30 days."

This involves deciding:
- **What is the target variable (output)?** → e.g., `will_churn` (Yes/No)
- **What are the input features?** → e.g., usage frequency, complaints raised, subscription plan, tenure

### Step 3: Identify the Type of ML Problem
Based on the target variable, decide the category:

| Question | ML Problem Type |
|---|---|
| Is the output a category (Yes/No, class label)? | **Classification** |
| Is the output a continuous number? | **Regression** |
| Is there no labeled output at all, just grouping needed? | **Clustering (Unsupervised)** |
| Does the system learn via trial, error, and rewards? | **Reinforcement Learning** |

> Example: Predicting churn (Yes/No) → **Binary Classification problem**.

### Step 4: Check Current Solution / Baseline (if any)
- Is there already a manual/rule-based process solving this problem?
- What is its current performance? This becomes the **baseline** your ML model must beat.
- Example: Currently, the support team manually flags "at-risk" customers with ~40% accuracy — your model should aim to beat this.

### Step 5: Get the Data
- What data is available? Where does it come from (databases, logs, APIs, third-party)?
- Is the data **labeled** (needed for supervised learning)?
- How much data is available, and is it sufficient?
- Is the data **static** (available all at once) or **streaming** (arriving continuously)? → decides Batch vs Online learning.

### Step 6: Decide Batch vs Online Learning
- If data changes slowly and can be collected in bulk → **Batch/Offline Learning**.
- If data streams continuously and patterns shift quickly (e.g., stock prices, live user clicks) → **Online Learning**.

### Step 7: Check Assumptions & Constraints
- **Latency requirement:** Does the prediction need to happen in real-time (milliseconds) or can it be batch-processed overnight?
- **Interpretability requirement:** Does the business need to *understand why* a prediction was made (e.g., loan rejection reasons are legally required to be explainable)?
- **Scale:** How many predictions per second/day are needed?
- **Compute/Budget constraints:** Is a lightweight model sufficient, or can we afford deep learning + GPUs?

### Step 8: Define the Performance Metric
Choose a metric that reflects the actual business goal, not just a generic one.

| Problem Type | Common Metrics |
|---|---|
| Classification | Accuracy, Precision, Recall, F1-score, ROC-AUC |
| Regression | MAE, MSE, RMSE, R² Score |
| Clustering | Silhouette Score, Davies-Bouldin Index |
| Ranking/Recommendation | Precision@K, NDCG, MAP |

> Example: For churn prediction, **Recall** might matter more than Accuracy — missing an at-risk customer (false negative) is more costly than a false alarm.

### Step 9: Deployment & Feedback Consideration
- How will the model's output actually be used? (e.g., trigger a discount email, flag for a human agent)
- How will you know if the model is working well after deployment? (monitoring, feedback loop, retraining plan)

---

## 3. Summary Flow of Problem Framing

```
Business Problem
      ↓
Define the goal in plain language
      ↓
Convert to ML terms (target variable + features)
      ↓
Identify ML problem type (Classification / Regression / Clustering / RL)
      ↓
Check existing baseline solution
      ↓
Assess available data (labeled? volume? static or streaming?)
      ↓
Decide Batch vs Online learning
      ↓
Note constraints (latency, interpretability, scale, budget)
      ↓
Choose the right evaluation metric
      ↓
Plan deployment & feedback loop
```

## 4. Worked Example: Framing a Real Problem

**Business Problem:** *"Our e-commerce company wants to reduce the delivery delays customers complain about."*

| Step | Answer |
|---|---|
| Business goal | Reduce delivery delay complaints |
| ML problem | Predict expected delivery time for each order before it ships |
| Target variable | `delivery_time_in_days` (continuous number) |
| ML problem type | **Regression** |
| Features | Distance, warehouse location, order weight, courier partner, day of week, weather |
| Baseline | Currently a fixed estimate is shown ("5-7 days") regardless of order details |
| Data | Historical order + delivery logs (static, large volume) → **Batch Learning** |
| Constraint | Prediction must be shown to the customer within 1 second of placing the order → low latency needed |
| Metric | **RMSE** (Root Mean Squared Error) — penalizes large delay errors more heavily |
| Deployment | Prediction shown at checkout; retrain model monthly with new delivery data |

## 5. Code: Implementing the Framed Problem (Regression Example)

Below is a simplified, end-to-end code example that reflects the framing above — predicting a **continuous delivery time** from order features. Comments explain each step in relation to the framing decisions made.

```python
# ==========================================================
# Problem Framing Recap:
# - ML Problem Type : Regression (predicting delivery_time_in_days)
# - Learning Mode    : Batch Learning (trained on historical bulk data)
# - Metric Chosen    : RMSE (penalizes large errors)
# ==========================================================

import pandas as pd
import numpy as np
from sklearn.model_selection import train_test_split
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.pipeline import Pipeline
from sklearn.linear_model import LinearRegression
from sklearn.ensemble import RandomForestRegressor
from sklearn.metrics import mean_squared_error, mean_absolute_error, r2_score

# ----------------------------------------------------------
# Step 1: Create a sample dataset
# (In a real project, this would come from a database/CSV/API)
# ----------------------------------------------------------
data = pd.DataFrame({
    "distance_km":       [5, 120, 45, 300, 15, 60, 500, 8, 220, 33],
    "order_weight_kg":   [1.2, 5.0, 2.3, 10.0, 0.5, 3.1, 15.0, 0.8, 7.5, 2.0],
    "courier_partner":   ["A", "B", "A", "C", "A", "B", "C", "A", "B", "C"],
    "day_of_week":       ["Mon", "Fri", "Wed", "Sat", "Tue", "Thu", "Sun", "Mon", "Fri", "Wed"],
    "delivery_time_days":[1, 4, 2, 6, 1, 3, 7, 1, 5, 2]   # <-- Target variable
})

# ----------------------------------------------------------
# Step 2: Separate Features (X) and Target (y)
# This mirrors the framing decision: target = delivery_time_days
# ----------------------------------------------------------
X = data.drop(columns=["delivery_time_days"])
y = data["delivery_time_days"]

# ----------------------------------------------------------
# Step 3: Identify feature types for preprocessing
# - Numerical features   : distance_km, order_weight_kg
# - Categorical features : courier_partner, day_of_week
# ----------------------------------------------------------
numerical_features = ["distance_km", "order_weight_kg"]
categorical_features = ["courier_partner", "day_of_week"]

# ----------------------------------------------------------
# Step 4: Build a preprocessing pipeline
# - Scale numerical columns (helps distance-based / gradient models)
# - One-Hot Encode categorical columns (models need numbers, not text)
# ----------------------------------------------------------
preprocessor = ColumnTransformer(transformers=[
    ("num", StandardScaler(), numerical_features),
    ("cat", OneHotEncoder(handle_unknown="ignore"), categorical_features)
])

# ----------------------------------------------------------
# Step 5: Split into Train and Test sets
# Mirrors the "baseline vs new model" comparison mindset —
# we hold out data to fairly evaluate the model afterward.
# ----------------------------------------------------------
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.3, random_state=42
)

# ----------------------------------------------------------
# Step 6: Build a full pipeline (Preprocessing + Model)
# Using RandomForestRegressor since delivery time likely
# depends on non-linear combinations of features.
# ----------------------------------------------------------
model_pipeline = Pipeline(steps=[
    ("preprocessor", preprocessor),
    ("regressor", RandomForestRegressor(n_estimators=100, random_state=42))
])

# ----------------------------------------------------------
# Step 7: Train (fit) the model on training data
# ----------------------------------------------------------
model_pipeline.fit(X_train, y_train)

# ----------------------------------------------------------
# Step 8: Predict on unseen test data
# ----------------------------------------------------------
y_pred = model_pipeline.predict(X_test)

# ----------------------------------------------------------
# Step 9: Evaluate using the metric chosen during framing (RMSE)
# Also showing MAE and R² for a fuller picture.
# ----------------------------------------------------------
rmse = np.sqrt(mean_squared_error(y_test, y_pred))
mae = mean_absolute_error(y_test, y_pred)
r2 = r2_score(y_test, y_pred)

print(f"RMSE: {rmse:.2f} days")
print(f"MAE : {mae:.2f} days")
print(f"R²  : {r2:.2f}")

# ----------------------------------------------------------
# Step 10: Predict delivery time for a brand-new order
# (This simulates how the model would be used in production)
# ----------------------------------------------------------
new_order = pd.DataFrame({
    "distance_km": [80],
    "order_weight_kg": [3.0],
    "courier_partner": ["B"],
    "day_of_week": ["Fri"]
})

predicted_days = model_pipeline.predict(new_order)
print(f"Predicted delivery time for new order: {predicted_days[0]:.1f} days")
```

### Explanation of the Code (Mapped Back to Problem Framing)

| Code Step | Why It Matches the Framing |
|---|---|
| `y = data["delivery_time_days"]` | Confirms this is a **Regression** problem — target is a continuous number, not a category. |
| `ColumnTransformer` with `StandardScaler` + `OneHotEncoder` | Necessary preprocessing since raw features include both numeric and categorical (text) data — models can't process text directly. |
| `train_test_split` | Creates a fair way to test the model on unseen data, similar to comparing against a baseline. |
| `RandomForestRegressor` | Chosen because delivery time likely depends on complex, non-linear interactions (distance × weight × courier), which tree-based models capture well. |
| `mean_squared_error` → `RMSE` | Directly reflects the **metric decided during framing** — RMSE penalizes large delay errors more, matching the business goal of avoiding big delivery mistakes. |
| Final prediction on `new_order` | Simulates real deployment — this is what would run "at checkout" as planned in the framing step. |

## 6. Key Takeaways

1. **Framing comes before coding.** A perfectly coded model solving the wrong problem is useless.
2. Every framing decision (target variable, ML problem type, metric, batch/online) directly shapes **what code you write later** — as shown in the mapping table above.
3. Always tie the chosen **metric** back to the **real business cost** of errors (e.g., RMSE for delivery delays, Recall for churn/fraud where missing a positive case is costly).
4. Framing is not a one-time step — as you learn more from EDA or initial modeling, you may need to **revisit and refine** the framing (iterative process, same as MLDLC).
